This guide is for wallet developers who want to wrap their existing secp256k1-blake160 lock with the firewall lock, so that spends from that wallet cell are checked against the blacklist at consensus.

<Aside type="caution" title="Adopting the firewall lock changes your CKB address">
The firewall lock is a different lock script than standard secp256k1. Using it produces a **different CKB address**. Any existing UTXOs at your current address must be explicitly spent into the new firewall-locked address — there is no in-place migration. Plan for this migration before deploying to users. If you later need to change which registry the lock references, you must migrate all cells again, because lock args are immutable after cell creation.
</Aside>

## What changes from the wallet's perspective

The lock script changes. The signing flow does not.

Your wallet still signs the CKB transaction hash with the same secp256k1 private key. The 65-byte signature still goes into `WitnessArgs.lock`. The firewall lock intercepts the spend, checks the outputs against the blacklist, and then forwards the signature to the inner lock (`spawn-aware-secp256k1`) via `spawn_cell`.

## Build the firewall lock script

```ts
import { buildFirewallLockScript } from "@ckb-firewall/sdk";

const firewallLock = buildFirewallLockScript({
  // The deployed firewall-lock code cell
  firewallCodeHash: "0x8192c9df809976ae9b093dd0d6b072a96101be8cffe61a7e9ac87c04e1f4dc54",
  firewallHashType: "type",

  // Check both lock_args and type_args of outputs
  flags: 0x03,

  // Which registry cells to consult
  registries: [
    {
      codeHash:    "0x5812b3f0f68ded4d61e8f12117caa011f295dbe88a29c07b86c9caec14bd6c55",
      hashType:    "type",
      typeIdValue: "0xc70a072cdfb7d25a5e92d27a47f9c8a0f30513de683e56e16d55ae30775f3951",
      required:    true,
    },
  ],

  // The inner lock — must match spawn-aware-secp256k1's on-chain type ID
  innerCodeHash: "0x9be62e0423d4278b15c071bb881a4ebf936f7e46b3df0f152de50ae416f54465",
  innerHashType: "type",

  // Your wallet's pubkey hash (same as standard secp256k1 lock args)
  innerArgs: "0x<your-20-byte-pubkey-hash>",
});
```

Use `firewallLock` as the `lock` field of the cell you want to protect.

## Pre-flight check before signing

Before presenting the transaction to the user for signing, run the pre-flight check:

```ts
import { findRegistryCell, fetchRegistryPayload, preflightCheck } from "@ckb-firewall/sdk";

// Always discover the current outpoint — it moves after each governance update
const { txHash, index } = await findRegistryCell("https://testnet.ckb.dev", registrySpec);
const registry = await fetchRegistryPayload("https://testnet.ckb.dev", txHash, index);

const decision = preflightCheck(tx.outputs, [registry]);

if (!decision.ok) {
  throw new Error(`Blocked: ${decision.reason} (code ${decision.code})`);
}
```

<Aside type="caution" title="Fetch a fresh registry outpoint before each check">
The registry cell moves after every governance update. `findRegistryCell` queries the CKB indexer to always return the live cell — see [Finding the current registry outpoint](/getting-started/typescript-sdk/#finding-the-current-registry-outpoint) for the full spec values and details.
</Aside>

## Cell deps for spending

When building a transaction that spends the firewall-protected cell, include the required cell deps:

```ts
import { buildFirewallSpendCellDeps } from "@ckb-firewall/sdk";

const cellDeps = buildFirewallSpendCellDeps({
  firewallLockOutPoint: {
    txHash: "0x128193cc2d547b224ccf10a6e299cb0749c633c5f9354ff5a9a5fd3e894318d2",
    index: 0,
  },
  innerLockOutPoint: {
    txHash: "0x0fe5d47662724a3620c002683d8c3f38103359c7e1ca697196b39442317c709e",
    index: 0,
  },
  registryOutPoints: [{ txHash: "<current-registry-tx>", index: 0 }],
});
// add these to your transaction's cell_deps array
```

<Aside type="caution" title="Time-based entries require header_deps">
If the registry contains entries with an `expiresAt` timestamp, include `header_deps` with a recent block hash in every spending transaction. Without `header_deps`, the chain's median time evaluates to zero — all temporary entries are treated as permanently active and the transaction silently blocks spends it should allow. If you are unsure whether the registry has time-based entries, always include `header_deps`.
</Aside>

## Signing

No change. Sign the transaction hash with your private key and place the 65-byte signature in `WitnessArgs.lock`. The inner lock reads it from there via the firewall's spawn delegation.

## Summary

<Steps>
1. Build the firewall lock script with `buildFirewallLockScript`
2. Create or migrate wallet cells using this lock script
3. At transaction-build time: fetch the live registry, call `preflightCheck`
4. Add `buildFirewallSpendCellDeps` to the transaction's `cell_deps`
5. Sign as normal — the secp256k1 signing flow is unchanged
</Steps>
