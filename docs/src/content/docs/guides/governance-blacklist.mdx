This page explains the full lifecycle: what happens when you propose an address, what validators do when they vote, what gets written on-chain, and what happens when a temporary entry expires.

## Proposals are local first, then anchored on-chain

The proposal starts as a JSON file stored at `~/.ckb-firewall/proposals/<id>.json` on your machine. Before it can be executed, it must be anchored on-chain as a `PBLK` proposal cell with `ckb-firewall anchor`.

Between `propose` and `execute`, votes and metadata still live in local files that participants share manually via `export` and `import`. The on-chain `PBLK` cell anchors the proposed registry transition and gives CKB consensus a real input cell whose age can enforce the review delay.

The `proposalIdHash` is a cryptographic hash of the proposal fields and locks them in place. Any modification to the proposal fields produces a different hash, which invalidates votes for that proposal.

## Step 1: Propose

```bash
ckb-firewall propose \
  --action add \
  --lock-args 0xdeadbeef... \
  --expires-at 0 \
  --evidence "https://explorer.nervos.org/transaction/0x..." \
  --classification theft \
  --severity high \
  --rationale "Address received proceeds from the Drainer exploit on 2026-05-15." \
  --proposer alice
```

All flags are interactive if omitted. After this command:
- A proposal JSON is saved locally with a unique `proposalIdHash`
- A 72-hour review window starts locally
- The address is **not yet blacklisted** — nothing has changed on-chain

Export and share the proposal with other participants:

```bash
ckb-firewall export --proposal <id> --out proposal.json
```

## Step 2: Other participants import and review

Each governance participant imports the proposal:

```bash
ckb-firewall import proposal.json
```

The import validates the `proposalIdHash` against the proposal fields — a tampered file is rejected before saving.

## Step 3: Anchor the proposal cell

Create the on-chain `PBLK` proposal cell. This is the cell that later appears as an input to the governance transaction, with a relative timestamp `since` proving it has aged for the review delay.

```bash
ckb-firewall anchor --proposal <id> --to-address <proposal-cell-owner-address>
```

For the production treasury flow, the command builds a typed `proposal-anchor` transaction funded by the registry treasury:

```bash
ckb-firewall anchor \
  --proposal <id> \
  --tx-out gov_anchor_tx.json
```

On canonical testnet, the deployed `proposal-anchor` code outpoint is used by default. For a private deployment, override it with `--proposal-anchor-code-tx` and `--proposal-anchor-code-index`.

If the treasury uses a custom lock script, include any required lock deps:

```bash
ckb-firewall anchor \
  --proposal <id> \
  --treasury-lock-dep <lock-code-tx>:<index>:code \
  --tx-out gov_anchor_tx.json
```

Sign and submit it with the treasury account:

```bash
ckb-cli tx sign-inputs --tx-file gov_anchor_tx.json --from-account <treasury-address> --add-signatures
ckb-cli wallet apply-txs --tx-file gov_anchor_tx.json
```

For a non-treasury registry, the command prints the exact `ckb-cli wallet transfer --to-data ...` command needed to create the cell. To run it directly:

```bash
ckb-firewall anchor \
  --proposal <id> \
  --to-address <proposal-cell-owner-address> \
  --from-account <funding-address> \
  --submit
```

If you used `--submit`, the CLI stores the proposal-cell outpoint on the proposal JSON. If you created the cell with the printed command or the typed treasury transaction, record the accepted outpoint once:

```bash
ckb-firewall anchor --proposal <id> --proposal-tx <anchor-tx-hash> --proposal-index <data-output-index>
```

<Aside type="note" title="The review delay is anchored to this cell">
The governance-lock checks the `since` field on the `PBLK` proposal input, not the registry input. CKB consensus only accepts the final update once that proposal input has aged by the required relative median-time-past delay.
</Aside>

## Step 4: Validators vote

Each validator reviews the evidence and votes with their secp256k1 private key:

```bash
ckb-firewall vote --proposal <id> --vote yes
# prompts: "Validator private key (32-byte hex):"
```

**What the vote command does:**
1. Derives the validator's compressed public key from the private key
2. Checks that this public key is in the authorized validator set (Merkle membership proof against the on-chain `validatorMerkleRoot` in the BLKL governance header)
3. Rejects the vote if the key is not an authorized validator
4. Signs the vote payload: `blake2b({domain: "ckb-firewall:vote", proposalIdHash, vote, timestamp, pubkey})`
5. Stores the vote locally with the signature and Merkle proof
6. Updates the `voteDigestHash` — a commitment to the full set of votes

After voting, the validator exports their updated proposal and shares it back:

```bash
ckb-firewall export --proposal <id> --out proposal-voted.json
```

Other participants import this to merge the vote:

```bash
ckb-firewall import proposal-voted.json
```

<Aside type="note" title="Votes authorize execution">
Each vote is a cryptographic signature stored in the proposal JSON. During execution, validator vote signatures and Merkle proofs are included in the transaction witness and verified on-chain. Validators do not pay fees to vote.
</Aside>

## Step 5: Execute on-chain

After the 72-hour review window passes and 3 of 5 validators have voted yes:

```bash
ckb-firewall execute \
  --proposal <id> \
  --tx-out gov_tx.json
```

**What the execute command does:**
1. Recomputes the `voteDigestHash` from stored votes — aborts if it doesn't match (tamper detection)
2. Verifies every vote signature against the voter's claimed public key
3. Verifies every vote pubkey has a valid Merkle proof against the on-chain validator set
4. Includes the yes-vote signatures and Merkle proofs in the witness for on-chain verification
5. Fetches the current registry cell from the RPC
6. Fetches the `PBLK` proposal cell and verifies its data matches this proposal
7. Builds the new BLKL v2 payload with the address added or removed
8. Constructs the GOV1 v4 witness binding the proposal, vote context, BLKL transition, proposal-cell hash, and review delay
9. Sets relative timestamp `since` on the proposal input
10. Writes the transaction to `gov_tx.json`

The transaction is then submitted:

```bash
ckb-cli tx sign-inputs --tx-file gov_tx.json --from-account <funding-address> --add-signatures
ckb-cli wallet apply-txs --tx-file gov_tx.json
```

Or pass `--sign` to `execute` to do this in one step.

**After the transaction confirms:**
- The old registry cell is consumed
- The anchored proposal cell is consumed and its remaining capacity is returned to the treasury when the registry declares treasury metadata
- A new registry cell exists with the address in the BLKL payload
- The address is now blacklisted — any transaction spending a firewall-protected cell that sends to this address is rejected at consensus
- The proposal status is updated to `executed`

If the new BLKL payload needs more registry capacity than the current registry cell holds, include treasury cells when building the execution transaction:

```bash
ckb-firewall execute \
  --proposal abc123 \
  --treasury-cell 0x...:0 \
  --treasury-lock-dep 0x...:0:code
```

If the update removes expired entries or otherwise shrinks the required registry capacity, the builder lowers the registry output capacity and returns the freed capacity to the treasury.

## Permanent vs. temporary entries

**Permanent entry (`--expires-at 0`):** The address stays blacklisted until a governance proposal explicitly removes it.

**Temporary entry (`--expires-at <unix-timestamp>`):** The firewall lock reads the chain's median block time and treats the entry as inactive once the chain time reaches `expiresAt`. The entry remains in the registry payload (takes up space), but spends to that address succeed.

<Aside type="caution" title="Temporary entries require header_deps">
For time-based entries to expire correctly, the spending transaction must include `header_deps` with a recent block hash. Without `header_deps`, the chain's median time evaluates to zero and all temporary entries are treated as permanent. The transaction does not fail with a clear error — it just silently enforces the wrong policy.
</Aside>

## What happens after an entry expires

When a temporary entry's `expiresAt` timestamp passes:
- The firewall lock treats it as inactive — spends to that address are allowed again
- The entry still takes up space in the registry payload
- **The address is not automatically re-listed** if it becomes active again — a new `add` proposal is required

To re-blacklist an address after expiry, create a new proposal:

```bash
ckb-firewall propose \
  --action add \
  --lock-args <same-address> \
  --expires-at <new-timestamp-or-0>
```

## Removing expired entries from the registry

Expired entries accumulate in the payload indefinitely. To remove them and compact the registry, submit a `remove` proposal:

```bash
ckb-firewall propose --action remove --lock-args <expired-address>
```

This goes through the full governance flow just like an `add`. The result is a new registry cell with the entry absent.

## Check the current status

```bash
ckb-firewall check --lock-args 0xdeadbeef...
ckb-firewall inspect
```

`inspect` shows all entries with their status (`active` or `EXPIRED`) and expiry dates.
