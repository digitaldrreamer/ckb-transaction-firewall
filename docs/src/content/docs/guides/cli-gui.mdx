<Aside type="caution" label="Experimental">
  GUI mode is an early-stage feature in an actively developed project. Expect rough edges — the interface may change significantly between releases and is not yet recommended for production governance flows.
</Aside>

`ckb-firewall gui` opens a local browser-based interface for validators who review blacklist proposals and vote. It is not a normal wallet safety screen. It runs entirely on your machine — a lightweight HTTP server serves the UI on loopback, and private keys entered for voting never leave localhost.

The default UI is intentionally vote-focused: proposals that need your vote are highlighted, and optional execution mechanics such as anchoring and transaction building are hidden unless you open a proposal and explicitly expand advanced actions.

## Launch

```bash
ckb-firewall gui
```

The server starts on port `7979` by default and opens `http://ckb-firewall.localhost` in your browser automatically. If port 80 is unavailable, it falls back to `http://ckb-firewall.localhost:7979` (or a random available port if 7979 is also in use).

## What's inside

The interface has three tabs:

- **Overview** — summary of open proposals, registry size, blacklist pool usage, treasury balance, and proposals waiting for your vote
- **Registry** — all current blacklist entries with expiry status and the same pool status banner
- **Proposals** — proposal list with voting controls and filters

From any proposal you can inspect the target address, evidence, rationale, vote totals, and cast your vote. You can export the proposal JSON to share with another validator. Advanced actions are collapsed by default.

## Validator flow in the GUI

For a validator, the normal flow is:

1. **Open proposals needing your vote** — use the Overview priority list or the **Needs my vote** filter.
2. **Review evidence** — open the proposal and read the evidence, rationale, severity, and current vote totals.
3. **Vote** — click **Cast vote**, choose yes/no/abstain, and enter your validator private key.
4. **Share if needed** — export proposal JSON when another validator needs the latest votes.

Validators do not need to anchor proposals or execute transactions during the normal voting flow.

<Aside type="note" title="Why the anchor step exists">
The anchor cell is what lets CKB enforce the review delay on-chain. Validators do not normally handle it in the GUI. If you need to prepare or record an anchor, or build an execute transaction after validator approval, open a proposal and expand **advanced actions**.
</Aside>

<Aside type="tip" title="Pool funding visibility">
The Overview and Registry tabs show blacklist pool usage. If usage reaches 70%
or more, the banner asks users to donate CKB and shows the treasury donation
address from the registry metadata.
</Aside>

## Options

| Flag | Default | Description |
|------|---------|-------------|
| `--port <n>` | `7979` | Port the app server binds to |
| `--no-open` | — | Start the server without opening the browser |

```bash
# Custom port, no auto-open
ckb-firewall gui --port 8080 --no-open
```

## Portless URL

On Linux, you can get the clean `http://ckb-firewall.localhost` URL (no port number) by granting Node the ability to bind port 80 without root:

```bash
sudo setcap cap_net_bind_service+eip $(which node)
ckb-firewall gui
```

On macOS and Windows, running with `sudo`/Administrator is sufficient.

## Security note

The GUI server listens on all loopback addresses (`127.0.0.1` and `::1`) and enforces at the handler level that only connections from loopback are served. Private keys submitted through the vote form are converted to bytes and zeroed immediately after the cryptographic operation — they are not stored or logged. Note that JavaScript strings are immutable; the key material briefly exists as a string in V8 heap during transmission and JSON parsing, and cannot be zeroed at that stage. For highest assurance, use an air-gapped machine.
